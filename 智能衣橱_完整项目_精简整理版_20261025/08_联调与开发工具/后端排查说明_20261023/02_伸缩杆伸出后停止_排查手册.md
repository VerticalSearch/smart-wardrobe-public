# 伸缩杆伸出后停止：按证据定位

现场原话：“只有伸缩杆伸出去了，其他都没动。” 本轮没有设备实时日志，下面的分支需要用现场证据选择。

## 首先区分三种情况

| 现场记录 | 判断 | 下一项检查 |
|---|---|---|
| 下发12，收到同ID的12/done | 固件完成了“存衣准备”；后续需要人工挂衣及缩回入口 | 页面是否显示“缩回”；云端业务流程是否误把12当完整任务 |
| 下发12，但没有12/done | 机构位置不代表状态机结束；也可能终态链路丢失 | 主板2状态机与0x12回传→主板1 @TASK→网关rx→页面匹配 |
| 下发6或11，伸出/停住 | 不能套用“12正常等待”的解释 | 核对实际串口动作号/目标C点、主板1forwarded、主板2running/结果/当前步骤、部署版本 |

**一键启动的当前行为是12。** `newStore()`仅发送12并等待done，然后进入`await-retract`；`retractAndStartStore()`才发送13，等done后发11。主板2状态机在`STORE_PREPARE`模式完成伸出时显式跳到END。这是本轮核对源码确认的行为，不是对现场下发号的推测。

## 建议后端按这个顺序采证

1. 保存本次云任务记录及发布原文：task_id、type、完整payload、command.id、action_id、target_c、时间、topic、QoS/retain、发布结果。写数据库成功与MQTT发出分别记录。
2. 使用只读采集工具保存网关 `/api/status`、`/api/inventory`、串口日志。检索同一次命令的`last_command`、`cloud_rx`、`uart_tx`、`tx`、`rx`；确认不是只发了单轴`stepper_move`、调试动作5或动作12。
3. 把命令按实际顺序排成：12 sent → received → forwarded → running → done → 人工确认 → 13同链路 → 11同链路。最先缺失的阶段就是下一步排查层。
4. 有12/done却没有“缩回”：比较ID是否完全相同、页面是否旧缓存、真实打开地址是否`/cloud`、响应文件哈希是否等于本包。新页面里“缩回”只在`await-retract`显示。
5. 点了缩回却没有13的串口tx：看HTTP响应正文及控制台错误。收到HTTP200也要检查`ok/serialOk`。库存动作走旧`/api/control`或直接`POST /api/tasks`会409，不能忽略。
6. 有13/done却没有11：看`/api/hardware/task-dispatch`、云建任务响应ID、库存槽位预留失败、回滚信息。云任务创建超时或无可解析task_id时，当前实现不会继续发串口。
7. 有11 tx但板端不运行：看`received/forwarded/error`，目标C点1–12是否合法、主板1活动任务是否未清、主板2是否busy。需要硬件人员进一步读实际变量和版本，不能靠云端状态代替。
8. 第一条真正完成后第二条不执行：检查终态消费者是否按detail解析MQTT；command_id是否复用；库存`active_transaction`；主板1任务锁；页面取衣后的`await-reset`。逐层保留时间线。

在保留现场状态与日志之前，不要把“重启/清空库存/删除任务”当作排查第一步。槽位释放必须有实际物理位置依据，防止一次软件重置掩盖未完成动作。

## 已确认的代码问题与边界

### A. 长ID完成匹配缺陷（本轮Python+实际页面函数离线复现）

原始ID：`store-after-photo-task-msu96o4n`；发往串口：`store-after-photo-task-m`。网关库存模块能以前缀兼容完成提交；`_handle_serial_event()`仍把短ID保存进`task_events`，页面`waitForTaskTerminal()`用完整ID精确查找，因此等到超时。默认等待10分钟。

这发生在动作11阶段，和12只伸杆应分开定位。建议修复时统一端到端ID长度/字符约束，并在库存解析到完整事务ID后将规范ID传给页面/后端；同时保留原始回执ID。不能只改主板1缓冲区。

### B. MQTT终态外层缺少关联ID（本轮离线复现）

`_handle_serial_event()`调用 `publish_status("task", line, stage="board1_task")`，未传command_id。消息detail有`@TASK|...|id=...|state=done`，外层`command_id=""`。后端若只认外层ID或只认`status=done`会漏掉完成。需后端补交订阅消费代码，确认它是否解析这个格式；尚未证明现场因此堵塞。

### C. 缺少终态/复用ID（本轮离线复现）

向库存发出新存衣事务而不注入done，下一不同ID报`inventory transaction ... is still running`；相同running ID返回“already dispatched”，串口不重发；已完成ID再次发送报“already done”。这解释了为什么幂等重试和新任务必须有不同语义。带正确终态及不同ID的三个连续存衣事务在离线环境均成功，所以代码不是普遍只能跑一条。

### D. 固件完成回传（静态核对，未现场验证）

主板2主循环调用 `Board2_ActionList_Task()` 和 `Board2_LinkTaskStatusService()`；后者在状态机结束后发送done/error/stopped。主板1只有收到终态才释放当前任务锁。需核对双板实际烧录版本、回传串口线路及busy/队列计数。包中既有HEX不是部署证明。

## 后端同事需要补充的材料

- 远端云服务版本/commit、任务API处理器、调度worker和MQTT发布/消费源码。
- 故障这一次的实际任务JSON、下发消息、消费到的全部状态消息及数据库状态迁移。
- 第一条和后续任务是否复用了同一command.id；上层是否只创建任务却未发布下一阶段。
- 云端是否自动在收到12/done后推进；当前产品是否要求人工挂衣确认，确认事件来自哪里。
- 现场网关服务真实工作目录、页面哈希、双板固件版本或读取哈希。不得用包里代码替代实机核验。

建议先用离线脚本完成协议对齐，再由现场人员在确认机构位置、挂衣状态与可停止条件后验收12→13→11的完整流程。本包未执行真实动作验收，也没有代做修复部署。
